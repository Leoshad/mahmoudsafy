# One More Race

A lightweight pixel platform race in Do Together. Solo against a deterministic computer or a shared race between the two authenticated members. One finish decides the match. Shared forfeits are optional and require both players to tap Ready. This first version does not add race wins to the crown standings.

The server advances both runners at the same fixed 60 Hz physics step. Clients submit only direction and jump edges; supplied positions and finishes are ignored. A 32-bit random seed produces six short obstacle sections (gaps, moving platforms, crumbling bridges, timed gates, elevated shortcuts with lower stepping stones, and a speed boost into a long jump). The same course and clock serve both players. Rematches change the seed. Falls restart at the current section. No AI request or new paid infrastructure is needed.

Touch joystick supports horizontal movement and upward jump edges; keyboard arrows/A-D plus Space/W are also supported. The full-screen dialog supports portrait and landscape; rotate for more lookahead. Same account should use only one device per active race. Controls stop when released or the window loses focus. Connection loss pauses both runners after 2.5 seconds, allows a 60-second reconnection window, and cancels without a winner if unresolved. The server stores active races every two seconds and on lobby actions; restart resumes via a reconnect countdown. Latest 100 completed results are stored separately from existing game scores.

Verification: shared-seed equality; identical-input determinism; automated traversal of 30 courses; separate ready consent; stale/wrong-match input rejection; authoritative tie/finish once; disconnect pause; solo isolation; authenticated same-origin two-user HTTP flow; mock-DOM UI launch, touch movement, jump edge/release and sequence recovery. Full regression suite passes. Cloud browser blocked localhost preview, so physical phone rendering, touch comfort, and real Riyadh–Qena latency still require user playtesting. Procedural pixel characters are stylized, not photo-exact portraits.

Revision 2 (superseded): immediate persistent client prediction with bounded server corrections, faster running, jump buffering and coyote time, 0.3-second respawn, forced LTR and lane-matched progress bars. Domino felt-green palette and existing plum/gold controls. A clean run is roughly 18–25 seconds; failures extend this. Old version-1 sessions are discarded on startup to avoid different client/server courses; completed results are preserved. Physical phone playtesting remains outstanding.

Revision 3: input-frame protocol replaces server-arrival controls and position corrections. Each client runs fixed 60 Hz steps immediately and sends bounded batches of numbered inputs. The server replays the same frames, validates sequence/rate, and returns an acknowledged frame. The client replays its unacknowledged commands from that exact state. Obstacles and collisions use the same frame clock. The first finishing frame wins, with result resolution waiting for the other runner to reach that frame; tied frames tie. Network delays do not alter the recorded jump timing. Pending input is capped at two seconds; prolonged loss pauses the room. Opponent rendering is smoothed separately and never changes local physics. This protocol suits separate non-interacting lanes, not direct player collisions.

Touch is joystick-only. Raising the stick keeps the previous horizontal direction unless a new horizontal direction is given. Countdown is large and centered; controls are disabled until GO. Compound stepping gaps, narrower moving platforms, missing crumble tiles, a moving upper-route hazard and a tighter boost jump replace the easy straight crossings. Frame-replay tests cover 100/350ms one-way jittered delays, retries and ordering; drawing work clips offscreen floor detail. Version-2 pending races are reset on update to prevent mixed protocols. Real mobile frame rate and touch feel remain unverified here; cloud browser cannot reach this local preview.

Start/input fix: the stick stays visible and accepts a held direction during countdown, but physics begins only when racing. Countdown updates no longer clear pointer capture state. Computer authority is capped to human-submitted frames; its client display replays deterministic bot controls to the same local frame, preventing an artificial network head start. Countdown/GO never intercepts touch. Jump uses separate raise/reset thresholds to prevent accidental retriggers near the threshold. Tests cover held countdown input through GO and zero bot advance before gameplay frames. Physical phone testing remains outstanding.
